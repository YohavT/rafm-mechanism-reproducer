End-to-end workflow

From the upload of the Harel audit PDF (4 199 pages) to the simplified Excel model reproducing the management fee + BOR mechanism for old-adif participating products.

Bird's-eye view

Guiding principles applied throughout

1. No hallucination. Every value, every dependency, every rule comes from the code in the PDF. When the code does not say something, we say so explicitly rather than fill the gap.

2. Mechanical extraction, not LLM inference. Links between variables are computed by pattern matching on the code, not guessed by a language model. The LLM only explains structures that are already certain.

3. Verify before stacking layers. Each phase is validated (sanity tests, sample inspection) before the next phase is built on top. A defect found early costs an hour; the same defect found three layers later costs days.

4. Explicit caveats. Every simplification is named in writing inside the deliverable, not hidden in a conversation.

Industrialisation perspective — what could run in batch?

If you wanted to run this workflow on 10 audit reports at once:

Steps 1–9 + 17 (the green ones) — pure code. They run unattended. You get, for each report: the parsed hierarchy JSON, the level-by-column Excel, the empty Excel scaffold. Cost: cheap, fast, reproducible.

Steps 10–16, 18 (the yellow ones) — these require either an LLM with domain knowledge of life-insurance modelling, or a human actuary. This is where targeting, classification, algebraic decomposition, and mechanism interpretation happen. Cost: real (either LLM tokens with review, or human time).

Steps 4, 5, 9, 19 (the orange ones) — code does the heavy lifting, but a moment of inspection or methodology choice is required. Typically: validate one sample manually, then trust the batch.

Bottom line. Roughly half the workflow industrialises trivially. The other half — the value-adding interpretation work — is the part where you need either an LLM in the loop or an experienced reviewer. That's the part to budget for.

What the user prompts reveal — implications for agent design

This conversation produced 7 critical user prompts that prevented or fixed errors. They split into three types, and each type maps to a specific feature an agent would need.

Type 1 — CADRAGE prompts (system prompt material). Examples: "no hallucination", "verify yourself", "go step by step". These were stated upfront and applied throughout. An agent must encode them as constraints in its system prompt, not just trust they'll be remembered. They are non-negotiable behavioural rules.

Type 2 — SCOPE prompts (conversational steering). Examples: "no need for formula contents, only titles", "Excel in English, no French", "focus on full vs fixed". These narrow or expand the work. An agent must actively elicit scope at each major step rather than assume. Better to ask "are you sure you want everything or just the structure?" than to deliver too much or too little.

Type 3 — CORRECTIF prompts (error catches). Examples: "where does this 0.15 come from?", "the formulas exist from page 2940", "have you checked you didn't miss a component?". These are the most revealing. They show that without the user, several errors would have been delivered as final output:
  • The 0.15 value was sourced from nowhere (hallucination)
  • Part 5 of the PDF was missed (parser limitation)
  • Several model components were initially omitted (insufficient self-review)
  • The fond 300 hypothesis required clarification (incorrect domain assumption)
For an agent to be reliable without these user catches, it would need:
  • Source-attribution discipline. Every value cited must reference its origin in the parsed data (formula number, page). Values that cannot be traced are flagged.
  • Mandatory self-review steps. After each major output, a separate verification pass that compares the output to the source code.
  • Conservative defaults. When the agent isn't sure (e.g. parser found 13 blocks where it should find thousands), it must halt and ask, not push forward.
  • Coverage checks. When listing components of a mechanism, an explicit "what might I be missing?" pass.
Bottom line. The CADRAGE prompts make the agent safe. The SCOPE prompts make the agent useful. The CORRECTIF prompts reveal the gaps in autonomy that the agent's architecture must fill to operate without a human in the loop.

Lessons learned (to apply on the next audit report)

  1. Use pymupdf, not pdfplumber, for large PDFs (>1 500 pages). Speed and memory.
  2. Test title detection on both layouts from the start: single-line and two-line. RiskAgility outputs may use either.
  3. Do not assume the document has 4 parts. Part 5 (Appendix with formulas) exists in some reports but not others. Make the parser tolerant.
  4. Build a duplicate-cleanup step at the end of parsing — false-positive titles from numeric values in body text will happen.
  5. Read formulas in their natural order of computation (rates first, then fees, then balance updates) — not in numeric order of section IDs.
  6. When narrowing down to a mechanism, search by both name AND content keywords, then triage explicitly into "computes vs consumes".
  7. Algebraic decomposition before numerical example. The example only confirms the algebra, not the other way around.
  8. Always test the negative-return case for any fee mechanism — it usually exposes the asymmetric / debt-deferring branches.
  9. Write all caveats into the deliverable itself, not just into the chat. The user will open the file in two months without the conversation context.
