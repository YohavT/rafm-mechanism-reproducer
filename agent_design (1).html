Agent design — Mechanism-to-Excel reproducer

A POC that takes a parsed actuarial model (hierarchy + formulas) and a user's description of a mechanism, and produces a working Excel file reproducing that mechanism. Demonstration use case: management fee + BOR for Harel old-adif participating. The tool itself is mechanism-agnostic — the user specifies which mechanism via a prompt.

1. What this tool does

Mission. Take a complex actuarial model (e.g. RAFM) whose mechanisms are implemented in source code, and reproduce one selected mechanism as a functional Excel calculation that an actuary can understand and re-derive.

Input. A parsed model — a hierarchy of formulas (names and structure) plus the verbatim contents of each formula's code. Parsing and hierarchisation are assumed already done.

Mechanism choice. The user describes the mechanism via a structured prompt (4 fields: intro, formula types, models, products). The information is intentionally approximate.

Demonstration case. Management fee + BOR for old-adif participating products in the Harel RAFM model. Proving feasibility on this case is the POC goal; the architecture is mechanism-agnostic.

Design philosophy

PrincipleHow it is enforced
No hallucinationEvery cited formula number, page, code excerpt must originate from the input. Validators check this after every LLM call.
LLM handles semantics, Python handles renderingThe Excel file is generated by deterministic Python from a validated JSON spec. The LLM never writes openpyxl code.
Verify before stackingEach stage validates before the next runs. A failed Stage N never reaches Stage N+1.
Human-in-the-loop on critical interpretationTwo explicit checkpoints (after Stage 1 and after Stage 2) where the user confirms or corrects.
Halt rather than guessWhen the LLM cannot produce a complete, source-grounded output, it returns a halt signal rather than fabricating.

2. Technical stack

Stack choice
  • Instructor — forces every LLM call to return a Pydantic-validated structured object, with automatic retry on parsing/validation failure. The single most important library in the stack.
  • Native SDK — Anthropic SDK or Azure OpenAI SDK depending on Milliman access (claude-opus-4-5 primary candidate; gpt-5 secondary).
  • openpyxl — Excel file generation (deterministic template).
  • Pydantic v2 — schema definition for every LLM output.
  • Python orchestration — plain functions calling stages in order. No heavy framework.

Why not LangChain/LangGraph? The pipeline is linear with two checkpoints; it does not need a graph. Plain Python keeps the code auditable (a virtue for an AI-security context) and avoids dependency on a framework with frequent API changes. The architecture is compatible with a future LangGraph port if the tool grows beyond a single linear pipeline.

3. Pipeline overview — 7 stages

4. Cadrage rules (prepended to every LLM call)

Permanent system instructions
1. No hallucination. If a value, formula, number, or name is not explicitly
   present in the input you were given, do not output it. Use null and
   explain in a comment field.

2. Verify yourself. Before returning, re-read your output and check every
   citation against the inputs. If a citation cannot be confirmed, remove
   the corresponding assertion.

3. Stay structured. Return ONLY valid JSON conforming to the requested
   schema. No prose outside the JSON fields.

4. No filler. Avoid commentary words ("honestly", "of course",
   "interestingly"). Output is consumed by a downstream program.

5. Halt rather than guess. If the input is insufficient, return
   {"halt_reason": str} and stop.

STAGE 1 — LLMUnderstand and frame the request

Purpose

Take the user's structured prompt and the model hierarchy (names only, no formula contents) and produce a clear interpretation of what mechanism the user wants to reproduce.

Inputs

Inputs to Stage 1
  • The hierarchy — names and structure only, no formula contents.
  • The user prompt, structured in 4 fields:
    • intro — what is the mechanism about
    • formula_types — types of formulas involved
    • models — which models are involved
    • products — which products are involved

System prompt

System prompt — Stage 1
You are an expert actuarial developer. You receive the hierarchy of a RAFM
model: formula names and structural names (model, inputs, variables, etc.).
The user describes what they want to understand and reproduce.

Your goal in this stage is to PRE-INTERPRET the user's request: confirm
what mechanism they are asking about, identify which parts of the hierarchy
are relevant, and surface ambiguities.

You do NOT yet receive formula contents. Work only from names and structure.

User information is approximate. The user knows the model partially and
provides a best guess. Translate that guess into a precise interpretation
and flag uncertainties.

Return ONLY valid JSON:
{
  "interpretation": str,
  "relevant_branches": [str],
  "assumptions": [str],
  "ambiguities": [str],
  "confidence": "high" | "medium" | "low",
  "halt_reason": str | null
}

Validators

Post-LLM validation
  • Schema parses correctly.
  • Every relevant_branches path exists in the hierarchy.
  • If confidence == "high" but ambiguities is non-empty, retry with a warning.

Checkpoint 1 (human)

What the user sees and does
The interpretation, relevant branches, assumptions, ambiguities.

Actions: approve / correct the interpretation / resolve ambiguities. On correction, Stage 1 is re-run with the correction in context.

STAGE 2 — LLMPre-select relevant formulas

Purpose

Using the validated interpretation from Stage 1 and the hierarchy, select the formulas that define the mechanism. Identify dependencies so the next stages have a complete subgraph.

System prompt

System prompt — Stage 2
You are selecting formulas to reproduce a mechanism in Excel. The user's
intent has been confirmed in Stage 1.

SELECTION PRINCIPLES
- Distinguish formulas that DEFINE the mechanism from those that CONSUME
  it. Definers go in "selected"; consumers go in "consumers_for_info".
- Identify dependencies: if formula X is selected and it calls formula Y
  (directly or via -> delegation), Y must also be selected.
- Prefer minimal selection: 4-12 formulas typical.
- When a formula delegates to a sub-model (obj->method), include the
  target formula in the sub-model.
- When a formula has conditional branches (e.g. par_nonpar=="P",
  old_adif), note which branches are in scope.

NAMING CONVENTIONS YOU MAY ENCOUNTER
adif, gimla, maslul = life insurance product structures
_cflow = cashflow model
par_nonpar = participating vs non-participating
old_adif = old-regime participating contracts
Do NOT invent meanings beyond what names and hierarchy reveal.

OUTPUT (ONLY valid JSON)
{
  "selected": [
    {
      "numero": str,
      "titre": str,
      "role_one_line": str,
      "why_defining": str,
      "branches_in_scope": [str]
    }
  ],
  "consumers_for_info": [
    { "numero": str, "titre": str, "consumes_what": str }
  ],
  "dependencies_followed": [
    { "from": str, "to": str, "reason": str }
  ],
  "concerns": [str]
}

Validators

Post-LLM validation
  • Schema correctness.
  • Every numero exists in the hierarchy.
  • Title match for every numero/titre pair.
  • Count: 3-12 in selected; flag outside range.
  • Dependency closure: every numero in dependencies_followed exists in selected or consumers_for_info.

Checkpoint 2 (human)

What the user sees and does
The selected formulas with role and rationale, plus consumers and dependencies.

Actions: approve / remove items / add items / request explanation. After a correction, Stage 2 is re-run with the previous selection and the correction passed in context.

STAGE 3 — MECHANICALExtract formula contents

For each formula in the approved selection, retrieve its verbatim contenu from the parsed JSON. Pure Python, no LLM.

What this stage does
  • Lookup each numero in the parsed JSON
  • Attach the full contenu (verbatim source code) to each entry
  • Pass the enriched selection to Stage 4
Failure mode: if a numero from the approved selection is not found, halt and escalate.

STAGE 4 — LLMDecompose the formulas

Purpose

Read the full source code of each selected formula. Identify branches, isolate remarkable sub-expressions, and derive any key algebraic identity (such as "rate_full − rate_fixed = v × Y" from the reference case).

System prompt

System prompt — Stage 4
You are reading the verbatim source code of selected formulas. Decompose
each one into its analytical structure: identify inputs, intermediate
quantities, branches, and any sub-expression that appears repeatedly and
deserves to become a named auxiliary variable.

GUIDANCE
- For each formula, list all inputs (variables and parameters used).
- For each formula, list all branches (conditional paths) with their tests.
- Identify shared sub-expressions across formulas: if the same expression
  appears in 2+ formulas, name it (it becomes an Excel column).
- If two formulas differ only in one factor or term, articulate the
  difference algebraically.
- Identify temporal dependencies: formulas that call themselves at t-1.

OUTPUT (ONLY valid JSON)
{
  "formulas": [
    {
      "numero": str,
      "titre": str,
      "inputs_used": [str],
      "branches": [
        { "condition": str, "scope_relevant": bool, "returns": str }
      ],
      "temporal_self_reference": bool
    }
  ],
  "shared_subexpressions": [
    { "name": str, "expression": str, "appears_in": [str] }
  ],
  "key_identities": [
    {
      "identity": str,
      "source_formulas": [str],
      "derivation_summary": str
    }
  ],
  "concerns": [str]
}

Validators

Post-LLM validation
  • Every numero in formulas matches Stage 3's input.
  • Every formula in shared_subexpressions.appears_in exists in formulas.
  • key_identities.source_formulas all exist in the selection.

STAGE 5 — LLMProduce the Excel JSON specification

Purpose

Convert the Stage 4 decomposition into a complete specification of the Excel model: inputs sheet, scenario, calculation columns (in topological order), color rules, notes.

System prompt

System prompt — Stage 5
You are producing a complete Excel specification for the mechanism analysed
in Stage 4. The specification will be rendered by a deterministic Python
template — fill the structure, do not write code.

RULES
1. Every "calculations" entry MUST cite a source_formula_number from
   Stage 4. Never invent.
2. Every formula in "calculations" MUST reference only inputs declared in
   "inputs", or calculations whose column_name appears EARLIER in the list.
   No forward references.
3. If a default value cannot be derived from sources, set
   "default_value": null and explain in "comment".
4. Distinguish "always_computed" calculations (every period) from
   "conditional" (with a test).
5. The "scenario" must exercise both regimes of the mechanism. Default
   suggestion: 24 periods alternating regimes.

OUTPUT (ONLY valid JSON, exact schema)
{
  "mechanism_name": str,
  "scope_description": str,
  "key_relation": { "identity": str, "source_formulas": [str] },
  "inputs": [
    {
      "name": str,
      "label": str,
      "default_value": number | null,
      "format": str,
      "comment": str
    }
  ],
  "scenario": {
    "driving_input": str,
    "n_periods": int,
    "default_values": [number]
  },
  "calculations": [
    {
      "column_name": str,
      "label": str,
      "kind": "always_computed" | "conditional",
      "formula_excel": str,
      "condition_excel": str | null,
      "format": str,
      "depends_on": [str],
      "source_formula_number": str,
      "source_excerpt": str
    }
  ],
  "color_rules": [
    { "rule_excel": str, "background_hex": str, "label": str }
  ],
  "notes": [ { "section": str, "text": str } ]
}

Validators

Post-LLM validation
  • Schema correctness.
  • Source citation: every source_formula_number exists in Stage 4's output.
  • Topological order: every name in depends_on appears earlier.
  • Formula parseability: identifiers in formula_excel all appear in depends_on.
  • Scenario length matches n_periods.
  • Symbolic smoke test: evaluate the spec in Python on the default scenario; abort if non-finite values appear.

STAGE 6 — LLMSelf-review for omissions

Purpose

Compare the Stage 5 JSON spec to the verbatim source code (from Stage 3) and list what the spec simplified or omitted. Non-blocking — informs the user, written into the Notes sheet of the final Excel.

Why on the JSON, not on the Excel

Note
The Excel is a binary file with formulas in cells. The JSON spec expresses the same content with explicit structure, machine-readable. Auditing the JSON is equivalent to auditing the Excel content but much easier for an LLM. The Excel is generated downstream from a validated JSON, so auditing the JSON is sufficient.

System prompt

System prompt — Stage 6
You are auditing an Excel-model specification against its source formulas.
Identify what the specification has simplified or omitted compared to the
source code.

RULES
1. Read each source formula carefully. Identify every input, every branch,
   every term, every special case.
2. For each, check whether the specification covers it.
3. Be specific. Not "the model is simplified" but "claims_maturity_honi(t)
   appears in the source units_e formula but is absent from the spec.
   Impact: units stay larger than in the real model."
4. Classify each omission:
   - "deliberate"   — reasonable simplification
   - "branch"       — code branch not modelled
   - "concerning"   — may produce wrong results
5. Cite source_formula_number and excerpt for each omission.

OUTPUT (ONLY valid JSON)
{
  "omissions": [
    {
      "kind": "deliberate" | "branch" | "concerning",
      "summary": str,
      "impact_one_line": str,
      "source_formula_number": str,
      "source_excerpt": str
    }
  ],
  "overall_concerns": [str]
}

How the output is used

Wiring back
The omissions array is written into the Notes sheet of the Excel, grouped by kind. Concerning items first, highlighted; deliberate items last, neutral colour.

STAGE 7 — MECHANICALGenerate the Excel file

Excel structure

SheetContent
DocAll selected formulas (numero, titre, page, verbatim code). Source of truth.
InputsOne row per inputs entry, yellow value cells, named ranges. Scenario table below.
ModelProjection: one row per period, columns in order of calculations. Formulas with names resolved. Conditional formatting from color_rules.
NotesOne section per notes entry, plus the "What this model does not include" section populated by Stage 6 grouped by omission kind.

Validators

Post-generation validation
  • Recalc check: zero #REF, #NAME, #DIV/0, #VALUE errors.
  • Formula count = n_periods × |calculations|.
  • Named ranges: all inputs have defined named ranges.
  • Output sanity: all calculated values are finite on the default scenario.

On failure: halt; broken file kept for inspection; escalate to human.

Answers to the open questions

Q1 — Does Stage 1 need a memory system, and if so, what does it store?
No persistent memory system is needed for the POC. What is needed is in-session state: the validated Stage 1 output is held in the orchestrator's memory and passed to subsequent stages. The orchestrator's state is a Python dict containing the outputs of each stage. No database, no vector store, no embedding cache.

Inter-session memory (caching past mechanisms analysed by the user) is a V2 feature, not part of the POC.
Q2 — Should the instruction prompt specify how to select variables?
Yes, but with principles rather than procedure. The Stage 2 prompt embeds five selection principles (definers vs consumers, dependency closure, minimal selection, sub-model delegation, branch identification). These are derived from the reference conversation where these exact distinctions had to be made manually.

Domain context is provided sparingly. The prompt explains naming conventions (adif, gimla, _cflow, etc.) but explicitly forbids invention of meaning beyond what the hierarchy reveals. Over-injecting domain context increases the LLM's confidence and therefore its hallucination risk.
Q3 — How is memory managed across human corrections?
By rebuilding context at each turn, not by maintaining a persistent state in the LLM. On a re-run after a human correction:

  • The orchestrator prepares a new prompt containing: the original user prompt, the hierarchy, the previous selection, the human correction, and an instruction to reconcile.
  • The LLM produces a new selection.
  • The new selection replaces the old one in the orchestrator's state.
This is deterministic and auditable. The cost is a larger prompt each turn, which is negligible for the POC (3-4 turns maximum in practice).

Known limitations

Honest gaps in this design
  • Single-mechanism scope per run. If the user wants two mechanisms in the same Excel, they run twice and merge manually.
  • No incremental updates. Re-running with a different prompt restarts the pipeline; no diff-based update.
  • Domain knowledge ceiling. The LLM is competent on RAFM conventions but will struggle on niche mechanisms not documented in the parsed audit. Checkpoint 1 exists to surface this.
  • No automated numerical validation of the Excel. The pipeline checks Excel for syntactic errors (#REF, #NAME, #DIV/0) but does not re-execute the spec in Python to verify that cells produce the expected values. A formula translation error that does not crash Excel will not be caught automatically. The user is responsible for spot-checking key cells against the source.
  • No model versioning. If the parsed model evolves, previous Excels are not flagged as outdated.
  • Cost not budgeted. No token-cost estimation or alerting yet.

Concrete next steps for implementation

  1. Lock the Pydantic schemas. Translate the 6 JSON output schemas into Pydantic models. These are the contract.
  2. Build the Stage 7 Excel template. Port the openpyxl code from the reference work, parametrised by the Stage 5 JSON.
  3. Implement Stage 3 (mechanical lookup). Pure Python, low risk.
  4. Implement the validators. Mostly Pydantic schema checks + cross-references against the input hierarchy.
  5. Wire the orchestrator. Python script, one function per stage, state passed via a dict.
  6. Build a minimal interface. CLI or Jupyter notebook for the POC. Streamlit for demo if needed.
  7. Test on the Harel MF/BOR reference case. The reference conversation produced a known-good output. Reproducing it is the POC success criterion.
  8. Iterate on prompts. Expect 3-5 rounds of refinement.
